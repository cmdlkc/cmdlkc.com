## What this is

cmdlkc.com — Cem Dilekci's personal portfolio site. Hand-written, dependency-free HTML/CSS/JS pages: no build step, no package manager, no bundler, no test suite (one small Node script is the only exception — see "Auto-linked project images" below). Every page is opened by double-clicking the `.html` file or serving the folder statically; changes are seen on refresh.

The page titles, sidebar footer, and a couple of placeholder copy blocks still say "Studio Karbon" — leftover branding from earlier prototyping sessions. The projects in `config/09-projects.js` (In the Weeds, 4-Chambers, Iteration, ...) are placeholder content too, not real work, as is `config/14-about.js`'s `about.paragraphs` — swap them for the user's actual projects and about copy when that content exists.

**This machine has no Node.** `node` is not on PATH and is not installed anywhere findable, so `scripts/build-project-manifests.js` cannot currently be run — see "Auto-linked project images". Python 3 *is* available (`python`), which is enough to serve the folder: `python -m http.server 8000` from the repo root. Chrome is at `C:\Program Files\Google\Chrome\Application\chrome.exe` and can be driven headlessly (`--headless=new --dump-dom`, `--screenshot=`) to check a change actually renders.

## Repository layout

- `index.html` + `config/*.js` + `js/*.js` (root) — **the live site.** `index.html` is now only a loader: plain `<script>` tags, in order, no bundler. `config/00-header.js` creates `CONFIG` and must stay first; each later `config/NN-*.js` `Object.assign`s its own numbered section onto it; `js/page.js` is the whole drawing/interaction engine, `js/lens.js` the cursor lens, and `js/boot.js` checks everything arrived and starts it, so it must stay last. Adding a config section means three edits: the new file, a `<script>` line in `index.html`, and a line in `SECTION_FILES` at the top of `js/boot.js`. (This was one `index.html` + one `config.js` until recently; anything below that still says "config.js" means "the config/ files".) Promoted from `prototypes/logo-torus/v3.1/`: the C/D ring logo doubles as the site's menu, opening into a per-project scattered image feed. See `prototypes/README.md` and the top-of-file comments in `prototypes/logo-torus/v3.1/logo-torus-v3.1.config.js` for the full design history (v1.0 solid tumbling logo → v2.x wireframe slice-menu → v3.0 whole-page WebGL fluid → v3.1 dropped the fluid page for a small cursor-following lens).
- `images/projects/<slug>/` — one folder per project (slug matches that project's `folder` field in `config.js`). Drop a `cover.*` image and any number of other images in; see "Auto-linked project images" below and `images/projects/README.md`.
- `images/logo-ideas/` — reference images for the logo design, not used by any page.
- `scripts/build-project-manifests.js` — the one build step in this repo. Run manually after adding/removing project images.
- `archive/` — the site's previous root contents (an earlier `index.html`/`config.js` built from the `horizontal-gallery` prototype, plus loose pre-versioning drafts of `fluid-cursor` and `liquid-glass`). Kept for reference, not served.
- `prototypes/` — every feature/experiment, each in its own folder. See `prototypes/README.md` for the full, authoritative explanation of this system (read it before restructuring anything here). Key points:
  - A "version" is **two files that travel together**: `<name>-vX.Y.html` and `<name>-vX.Y.config.js`. They find each other by filename and must stay in the same folder with matching names, or the page shows an explicit error instead of failing silently.
  - `logo-torus/` keeps each version in its own subfolder (`v1.0` … `v3.1`); other prototypes (`horizontal-gallery`, `fluid-cursor`, `liquid-glass`) are flat since they only have one version.
  - To make a new version: copy both files, bump the version number in **both filenames**, and update the `<script src="...">` line in the new `.html` to point at the new `.config.js`. Never edit an old version in place — the number is there so there's always a known-good fallback.
  - Convention: `v1.0 → v1.1` for tuning/small changes, `v1.0 → v2.0` when the approach is fundamentally different.
  - Nothing in `prototypes/` is served live. Promoting a prototype to production means copying it up to the repo root as `index.html`, renaming its config to `config.js`, and fixing the `<script src>` reference — exactly what was done for v3.1. **The promoted root copy is allowed to diverge from its prototype source** (e.g. the auto-linking code below only exists at root) — don't try to keep them in sync.

## The config/ convention

The `config/` files load first and build a single global `CONFIG` object, one numbered section per file. Every tunable number — sizes, colors, timings, motion physics — lives there, each documented inline with its safe range and what happens at either extreme, plus a running "what changed from vX" history in `config/00-header.js`. When asked to change how something looks or feels, edit the relevant `config/NN-*.js`, not the drawing/interaction logic in `js/page.js`, unless the change is structural.

If any file fails to load, the page deliberately shows a visible on-page error **naming the file** rather than failing blank. That check is `start()` in `js/boot.js`: it tests for `CONFIG` itself, then for each section listed in `SECTION_FILES`, then for `buildPage` and `LENS`. Preserve that behavior if you touch it — and keep `SECTION_FILES` in step when you add or rename a config section, or a missing file will report the wrong name.

## Auto-linked project images

`config/09-projects.js` (`projects: [...]`) is the ring menu's content: one entry per slice, each with a `title`, `blurb`, an optional `cover` path, and a `feed` array mixing `{ type: 'text', body }` and `{ type: 'image', src, ratio }` items that lay out as a scattered column when the project opens. Any image `src`/`cover` left as `''` renders as a labelled placeholder block (`drawFramed()` in `js/page.js`) rather than breaking anything.

Each project also has a `folder` field (e.g. `'in-the-weeds'`). That's the auto-linking hook:

1. Drop images into `images/projects/<folder>/` — one named `cover.*` for the cover card, everything else for the feed, in filename sort order.
2. Run `node scripts/build-project-manifests.js` from the repo root. It scans every folder under `images/projects/` and writes a `manifest.json` into each, listing what it found.
3. `loadProjectImages()` in `js/boot.js` fetches every project's `manifest.json` on load and fills in that project's `cover` and feed `src` fields — but only fields still `''`; anything typed into `config/09-projects.js` by hand is left alone. This fetch runs to completion *before* `buildPage()` is called, so there's no image-popping-in-after-layout race to worry about.
4. If a manifest 404s (nothing dropped in yet) or the fetch fails outright (opened via `file://` double-click rather than a server — `fetch()` to a local file is blocked by the browser), the project just keeps its placeholder — the whole thing degrades silently by design.

This is the only place in the repo that needs Node — **and Node is not installed on this machine**, so step 2 currently cannot be run at all and manifests can only be written by hand (or by porting the script to Python, which is available). There's no watcher either — re-run the script by hand whenever project images change.

## Architecture of the live site (`index.html` / `config/` / `js/`)

`js/page.js` draws the entire page — logo, slice menu, hover previews, project feed — into one offscreen 2D canvas (`buildPage()`), then blits it to the visible `#glass` canvas each frame; a second small canvas (`startLens()`, only if WebGL2 exists and `config.lens.enabled`) redraws a locally-refracted circular patch around the pointer on top, reading back a crop of the already-drawn page. Drawing everything through one pipeline is what lets the lens sample pixel-accurate content, and it's also why `getImage()`'s cache + `drawFramed()`'s placeholder fallback are shared by both the ring's hover-cover and the open project's feed.

Key structural pieces inside `buildPage()`:
- **The letterform — D to D** — a D-shaped profile revolved around a vertical axis; a wedge is cut out, and the two flat cut faces are the letterforms. `cap()` (in `buildMesh()`, `index.html`) builds each cut face as a ribbon of quads between the outer profile and the counter, walking the D all the way round — bottom edge, bowl, top edge, spine. **Both caps get the complete loop**, are tagged `tcap` 1, and are forced to the flat, ungated `shade.capFaces` in `paint()` — never run through hover state or lighting, so both print at constant weight from every orientation.

  The two faces read as a D and its mirror. That's free, not special-cased: the profile is laid out radially (`place()`), so the bowl always sits at the larger radius, and "outward" points screen-left on the `th0` face and screen-right on the `th1` face. Which physical cap lands on which side of the screen falls out of `view.cornerTurn`/`ring.notchAt` in `config.js`, not from anything in the mesh.

  **Don't open one of them up.** Two attempts at turning the mirrored face into a C have been made and both reverted. Printing its spine fainter (a `tcap` 2 "bare" tag + a `shade.capBare` density) doesn't work, because `paintLines()` derives the silhouette from the depth buffer and ignores `tcap` and density entirely — the bar keeps a full-strength outline and you get a washed-out mirrored D. Deleting the spine quads outright removes the outline but punches a hole in the ring's surface and breaks the closed letterform. If the pair needs to read as something other than D-to-D, change the **profile** (`buildProfile`) so the section itself is that shape; don't delete quads from one cap or shade the two faces differently.
- **The ring/menu state machine** — REST → PROJECT (feed open, logo parked in the corner) or ABOUT (page zoomed into the centre star). REST is the menu: the ring holds one fixed pose (`restPose()`, opening towards the camera), hovering a slice previews it and pressing it opens the project directly. **Nothing moves on its own** — no idle spin, no throw/momentum. Dragging turns the ring freely; releasing eases it back to `restPose()` over `motion.returnTime`. An earlier version had a third state, TOP, a separate top-down slice menu you had to open first; it and its settings (`view.sizeTop`/`tiltTop`/`topOpenAt`, `motion.idleSpin`/`friction`/`flickSmoothing`/`maxSpeed`/`stopBelow`/`pauseSpinOnHover`) are gone, not merely disabled.
- **The about page** — pressing the centre star zooms the whole drawing into it: same pose, same ring, scaled to `view.sizeAbout` (9 windows across — deliberately far past "just gone", because a portrait window needs roughly twice a landscape one to clear) with the logo centre tweened to the star's resting spot, plus `dotZoomT` growing the star itself since it's drawn at a fixed pixel size rather than scaled with the ring. The copy in `config.about.paragraphs` then types itself in underneath: `layoutAbout()` wraps every line at full length up front and `aboutChars` is a running character budget `drawAbout()` spends, so nothing reflows as the text arrives. There is no scrolling there — long copy will run off a short window.
- **Shading** — the cube-cursor model from the other prototypes, ported here: one ink color, tone from dot density (Bayer dither) rather than paler shades. Hover shading fades in per slice; the two cut faces (C/D) are always shaded, independent of lighting, so they stay legible at every orientation. The Bayer tile is fixed to the *screen*, so it doesn't shrink with the logo — once the letter's stroke is narrower than a tile or so the dither stops being a texture and becomes a few holes punched through a shape too small to spare them. Below `shade.fineBelow` (rendered pixels of stroke width; 10, sitting mid-gap between the resting logo's ~16 and the corner mark's ~5, so the flip doesn't depend on a few pixels of window width) the logo counts as *small* and three things change together: the tile drops to `shade.fineMatrix` (2), a lit slice prints in a **faded ink** — the same dots, mixed `shade.highlightFade` (0.5) of the way to the paper, so the highlight reads as translucent — and the cut faces keep their own `capFaces` density *and* full-strength ink, so the C/D sit on top of that wash as letters. This faded ink is the one place on the site that breaks "tone comes from dot count, never from a paler orange", and it's deliberate. **Two other approaches were tried and rejected at this size**: printing solid (caps and highlight become one tone — an orange blob), and halving the highlight's dot coverage (with only four threshold positions, half the dots is a coarser pattern, not a lighter tone). Separately, `view.cornerOpaque` makes the ring's *surface* print paper rather than transparent while a project is open, so the feed scrolls behind the mark instead of through it (the hole in the middle stays see-through).
- **The project feed** — positions are randomized per project but from a fixed seed (`seeded()`), so a project scatters the same way every time it's opened rather than reshuffling.
- **The lens** — a small, self-contained refraction effect confined to a circle around the cursor (`radius` in `config.lens`), re-sampling and bending a patch of the already-drawn page every frame. It runs a genuine tiny fluid sim now (splat + advect, ported from `prototypes/liquid-glass` at `lens.simSize` resolution, minus that prototype's incompressibility solve) rather than the fixed analytic dome v3.1 shipped with — but unlike v3.0's page-wide fluid (removed for reading as too digital), this patch lives entirely in the lens's own local space and travels with the pointer, so it has no page-space memory to leave a wake in and settles to invisible within a fraction of a second of the pointer stopping.

## Working on this in more than one session at once

Splitting `index.html`/`config.js` into `js/` and `config/` was done specifically so two sessions can work at the same time without landing in the same file. There are git worktrees set up for it:

| worktree | branch | where |
| --- | --- | --- |
| main | `v6` | `G:\My Drive\g_Projects\Personal\Website\cmdlkc` (in Google Drive) |
| content | `v6-content` | `C:\Users\cemdi\cmdlkc-worktrees\content` |
| render | `v6-render` | `C:\Users\cemdi\cmdlkc-worktrees\render` |

The two extra worktrees deliberately sit **outside Google Drive**. Add another with `git worktree add -b <branch> C:\Users\cemdi\cmdlkc-worktrees\<name> v6`, and remove one with `git worktree remove <path>`. Merge finished work back with an ordinary `git merge` from `v6`.

Rules that matter, learned the hard way:

- **One session per worktree.** Two sessions in one working tree will clobber each other: each caches what it read, so a write from one lands on the other's stale picture of the file. This has already happened here — a file grew by 77 lines between one session reading it and writing it, and an in-flight refactor was silently built on the wrong line numbers.
- **Prefer disjoint files over disjoint regions.** Two sessions editing different sections of one big file merges fine in git but is still the risky case; two sessions editing different *files* is safe. That is what `config/NN-*.js` is for.
- **The main worktree is inside Google Drive**, so Drive can rewrite files under a running session. If a file's size or line count moves when you did not move it, that is the cause. When doing anything that depends on exact line numbers, re-measure immediately before writing, and guard the write (abort if the file is not the size you measured).
- **Verify a structural change actually still runs** before committing — there are no tests here. `python -m http.server 8000` plus headless Chrome (`--headless=new --virtual-time-budget=8000 --dump-dom` or `--screenshot=`) is enough to prove the page boots and draws.
